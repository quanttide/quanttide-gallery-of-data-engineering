# 数据需求

数据需求是这一层的名字，也是它要交付的东西：动手之前，先说清楚为什么做、为谁做、什么算成功。它是 XMUCPP 案例的价值合同，不写公式、表名与代码。

## 背景与问题

十年前的厦门大学 China's Prices Project（CPP），参考 MIT Billion Prices Project 与 Cavallo 的研究，依据中国官方 CPI 分类标准，每天从天猫和京东采集一千多个关键词、约五百万个数据点，编制中国高频线上价格指数。项目从个人电脑上的定时爬虫起步，后来搬到腾讯云服务器集群；从十三个人手动维护，走到自动化系统。

做这件事的理由很直接：传统 CPI 依赖人工调研与月度统计更新，时效性差、颗粒度粗、覆盖不全；电商数据更新快、覆盖面广、精度高，足以支撑按日构建的价格指数，形成对市场更灵敏的监测。

## 目标与非目标

要建成三件事：一套按日发布的全国线上价格指数；一套基于官方 CPI 分类、可与官方指数对标的分类指数；以及一条从采集、存储、计算到发布都能长期自动运行的链路。

同样明确的是三条边界：不重造官方 CPI 的统计方法与权重口径，只做对标；不覆盖线下零售渠道；不做价格预测。

## 成功指标

成功不以交了几份文档计，而以业务后果计。

| 指标 | 口径 | 目标方向 |
|:--|:--|:--|
| 覆盖商品数 | 每日采集到有效价格的商品数 | 稳定在 1000 余关键词所覆盖的量级 |
| 数据可用率 | 当日可参与计算的商品占应采商品的比例 | 相对基线不下降 |
| 指数连续率 | 日度指数可链式连接的天数占比 | 无断点 |
| 发布时延 | 采集完成到指数发布的时间 | 按日发布（T+1） |

## 范围

案例的对象是分类、商品与每日价格销量，平台取天猫和京东，粒度按日采集、按日发布；不区分各平台爬虫的历史版本，统一按日归档。

## 利益相关者

研究者关心指数能否对标官方 CPI、方法是否可解释；工程关心采集与计算能否稳定运行；业务关心指数能否按期对外发布；读者关心数值是否可信。

## 约束

约束有四条。合规上遵守平台规则、不采集个人数据；权限上只读源页面与源数据；可重跑，源数据按日归档、重跑不改历史；资源上受服务器限制，采集需分布式、存储需集中。

# 量潮搜索工程

量潮搜索工程负责解决从「信息在哪」到「把它取出来」：可索引化、索引的建立与更新、查询解析、召回、排序与质量评测。本案例按「需求 → 哲学意图 → 数学形式化验证 → 计算机实现」四层链路展开（一般框架见[首页](../index.md)），把「搜索效率低」这类模糊判断，转成可追溯、可证伪、可复现的数据产物。

## 数据需求

### 背景与痛点

多个智能体（pi、zed、hermes、hermes-backup、dsh、opencode）的搜索行为不稳定：同样的任务，有的会话几次搜索即命中，有的会话反复搜索仍拿不到可用结果。搜索低效直接拖低任务成功率，并消耗使用者对智能体的信任。

### 目标与非目标

- 目标：定位搜索低效的主因，形成可验证的改进方向，产出一份可复现的诊断。
- 非目标：本次不重写检索算法；不覆盖非搜索类工具的低效；不追求指标的全覆盖。

### 成功指标（业务口径）

成功不以「产出报告」计，而以业务后果的改善计。下列指标在本次诊断中先建立基线，后续迭代再对照改善；具体阈值与显著性判据在「数据规格」层以统计检验定义。

| 指标 | 口径 | 目标方向 |
|:--|:--|:--|
| 搜索相关失败率 | 含搜索会话中，因搜索失败导致任务失败的占比 | 相对基线下降 |
| 任务成功率 | 含搜索任务中，会话达成目标动作的占比 | 相对基线提升 |
| 低效会话占比 | 单会话搜索次数超过阈值的会话占比 | 相对基线下降 |
| 结果采纳率 | 搜索之后结果被后续动作消费的比率 | 相对基线提升 |

### 范围

- 来源：6 个智能体——pi、zed、hermes、hermes-backup、dsh、opencode。
- 时间：近三个月的会话。
- 对象：上述来源中全部含搜索工具调用的会话及其搜索事件。
- 版本：各来源取诊断期内的全部版本，不做版本切分。

### 利益相关者

| 角色 | 关心什么 |
|:--|:--|
| 研发 | 修复工具与提示词缺陷 |
| 算法 | 改进查询生成与召回 |
| 产品 | 决定搜索体验改进的优先级 |
| 使用者 | 任务能否一次做对 |

### 约束

- 数据权限：会话数据含个人与渠道标识，须按[首页](../index.md)「脱敏说明」脱敏后方可产出。
- 合规：凭据与密钥不得进入任何分析产物。
- 只读：不改动源数据。
- 一次性：本次为离线诊断，不引入在线系统改动。

## 数据意图

### 本体：搜索行为及其要素

先把「搜索」拆成可界定的对象，再谈它是否低效。

| 概念 | 界定 |
|:--|:--|
| 搜索行为 | 智能体为获取完成任务所需信息而发起的一次读类工具调用 |
| 查询 | 搜索行为的输入，含工具名与参数 |
| 结果 | 搜索行为的返回，含条数、是否为空/错误、字符数、可结构化性 |
| 任务目标 | 会话要达成的用户诉求 |
| 信息需求 | 为达成任务目标所缺的信息 |
| 工具预算 | 会话可用于工具调用的次数与时间上限 |
| 反馈信号 | 结果是否被后续动作消费 |

### 认识论：凭什么说它低效

- 判断基准是「相对任务目标」，不是搜索的绝对次数。
- 证据以会话轨迹（trace）为主，辅以结果与后续动作；必要时人工标注。
- 「低效」是相对量：查询漂移、重复搜索、结果未利用、过度搜索，出现任一即记为疑似低效。
- 局限：无真实任务成功标签，以代理指标（结果是否被消费、会话是否达到目标动作）近似。

### 目的论

本次取「解释」与「预测」：解释低效由何而来，预测哪些来源与会话更易失败。「控制」（在线干预）留待后续迭代。

### 价值论

低效相对于「任务目标达成」这一规范判定；工具预算与可解释性为次要维度。搜索次数多本身不构成低效。

### 视角

- 控制论：搜索是带反馈的控制回路（目标 → 查询 → 结果 → 动作）。
- 信息检索：查询与结果的相关性，召回与精度的权衡。
- 因果解释：把「低效」当作待解释的结果，追问其成因。

### 问题树

- 核心问题：搜索低效的成因，及其可验证的改进方向。
- 子问题：低效来自查询生成、检索环境、结果利用，还是策略与目标？
- 非问题：非搜索工具的低效；与任务目标无关的搜索。
- 边界与反例：成功任务中的多次搜索（如探索性检索）不计为低效。

### 假设登记

| 假设 | 内容 | 可证伪条件 |
|:--|:--|:--|
| H1 | 空结果率高的会话更易失败 | 空结果率与任务失败呈负相关或无关 |
| H2 | 连续搜索与结果未被消费正相关 | 连续搜索率与未消费率不相关 |
| H3 | 结果过载与有效命中率负相关 | 过载率与有效命中率不相关或正相关 |

假设在此仅登记初步表述与可证伪条件，形式化与检验见「数据规格」。

## 数据规格

### 形式化对象

| 对象 | 记号 | 说明 |
|:--|:--|:--|
| 会话 | s | 一次完整交互 |
| 轨迹 | τ = (a₁, a₂, …) | 会话内的动作序列 |
| 动作 | a | 一次工具调用 |
| 搜索事件 | e | τ 中被判定为搜索的动作 |
| 查询 | q | 搜索事件的输入 |
| 结果 | r | 搜索事件的返回 |

变量与随机变量：查询 q；结果特征——条数 n、是否为空 ∅、是否错误 ϵ、字符数 ℓ、是否可结构化 ρ；行为特征——连续次序 k、结果后首个非搜索动作、是否行动前再搜；时延 Δt。任务目标 g 与工具预算 B 作为外部给定。

### 操作定义

- **搜索判定**：一次工具调用满足任一条件即计为搜索——工具名 ∈ 搜索工具集（search_files、session_search、memory_search、grep、glob、find_path、list_directory）；或工具为 shell 类（terminal、bash）且命令行匹配搜索动词（grep、rg、find、fd、ls、tree）。
- **查询漂移** drift(q, g)：查询与任务目标的语义相似度低于阈值 δ。
- **结果被消费** consume(e)：结果之后的首个非搜索动作读用了该结果（读文件、引用等）。
- **结果未利用**：结果被消费为假。
- **过度搜索**：单会话或单目标内的搜索次数超过工具预算 B。
- **有效命中率**：结果非空、非错误且被消费的搜索 ÷ 搜索总数。

### 指标

分母默认为搜索总数，空结果率除外。

| 指标 | 定义 |
|:--|:--|
| 空结果率 | 结果条数为 0 的搜索 ÷ 能解析出结果条数的搜索 |
| 错误率 | 返回错误的搜索 ÷ 搜索总数 |
| 结构化结果占比 | 结果可解析为 JSON 的搜索 ÷ 搜索总数 |
| 结果体量 | 结果字符数 ℓ 的中位数、P90、最大值 |
| 过载率 | ℓ 不小于阈值（默认 8000）的搜索 ÷ 搜索总数 |
| 连续搜索率 | 连续次序 k > 0 的搜索 ÷ 搜索总数 |
| 搜完又搜未行动率 | 在调用非搜索工具前再次搜索的搜索 ÷ 搜索总数 |
| 会话内重复查询率 | 同一会话内归一化查询出现两次及以上的搜索 ÷ 搜索总数 |
| 搜索后读文件率 | 结果之后首个动作是读文件的搜索 ÷ 搜索总数 |
| 延迟中位数 | 结果时间戳与调用时间戳之差的中位数 |

聚合维度：全局、按来源、按会话三层，便于把结论下钻到具体来源与会话。

### 命题与假设（形式化）

失败 fail(s) 定义为会话未达到目标动作。

- H1：空结果率高的会话更易失败——检验 空结果率(s) 与 fail(s) 的关系。
- H2：连续搜索与结果未被消费正相关——检验 连续搜索率 与 未消费率 的相关性。
- H3：结果过载与有效命中率负相关——检验 过载率 与 有效命中率 的关系。

### 因果图

```
prompt_version → query_drift → result_unused → task_fail
retrieval_env  → query_drift
tool_budget    → result_unused
```

混杂变量：任务类型、来源、会话长度。H1–H3 目前是相关命题，因果方向须经识别策略确认（见「验证方法」）。

### 约束与不变量

- 搜索次数 ≤ 工具预算 B。
- 查询与任务目标的相似度 ≥ δ，否则记为漂移。
- 结果引用覆盖 ≥ γ。

### 验证方法

- 假设：零假设 H0 与备择假设 H1–H3。
- 统计检验：比例用两比例 z 检验，相关用 Spearman 或卡方；报告效应量与置信区间。
- 样本量：按基线效应量估算，控制 I 类错误。
- 偏差控制：按来源与任务类型分层，避免辛普森悖论。
- 因果识别：可行时用提示词版本的 A/B，或用反事实/断点回归；不可识别时只报告相关。

### 验收清单

- [ ] 每个指标可由清洗产物一键复算，数值一致。
- [ ] 每个命题给出检验统计量、p 值、效应量与置信区间。
- [ ] 相关命题与因果命题分列，未识别的不得冒称因果。
- [ ] 报告结论均可回指到具体指标与命题。

## 数据实现

### 采集

输入是各来源的本地会话数据，输出是统一原始区。

每个来源登记其本地位置与格式（消息型、编码型、编辑器、终端等不同类型）。能导出为 JSONL 的来源用其导出命令落盘，其余直接复制原始文件，统一写入 `data/raw/<来源>/`。采集后写 `data/raw/manifest.json`，记录每个来源的路径、会话计数与采集时间，用于核对完整性。约束是只读复制，不改动源数据；单个来源失败不影响其余来源。

### 清洗

输入是原始区，输出是归一化后的四张表。

归一化把每个来源的会话转换成统一形状：会话携带元数据（编号、来源、标题、模型、起止时间）与消息列表；assistant 消息携带工具调用（工具名与参数），工具结果消息携带调用编号与结果文本。不同来源的工具调用结构差异在此抹平。搜索判定与特征抽取按「数据规格」的操作定义执行，实现层不另立定义。

产物为四张 Parquet 表：会话表、消息表（带搜索相关标注）、工具调用表（参数已解析为对象）、搜索事件表（附查询、结果与行为特征）。同时写清洗清单，记录四表行数与按来源的搜索计数。

### 分析

输入是清洗后的搜索事件表，输出是指标 JSON。按「数据规格」的指标定义与聚合维度计算；分母、阈值与分组口径均以规格层为准。

### 验证

输入是指标与搜索事件表，输出是检验结果。对 H1–H3 按「验证方法」执行：计算检验统计量、效应量与置信区间；可行时做因果识别（提示词版本 A/B 或反事实），不可识别则只报相关。检验结论与原始指标一并落盘。

### 报告

输入是指标 JSON 与检验结果，输出是 Markdown 报告。报告固定包含：总览、按来源、结果质量、结果体量、行为模式、搜索后首个动作分布、每会话摘要（截断只展示前若干名），末尾附诊断与证据强度。报告与指标 JSON 一并写出，两者数值一致；任何结论都必须回指到具体指标与命题，不得由模型自由生成。

### 追溯与质量校验

- 追溯矩阵：业务成功指标 ← 规格指标 ← 命题 ← 报告章节，逐列可回指。
- 质量校验：采集后核对 manifest 行数；清洗后核对四表行数与搜索计数；分析后核对报告与 JSON 数值一致。
- 版本管理：数据、代码、报告各自带上版本与时间戳。

### 复现入口

同一条命令行工具提供五个子命令——`collect`、`clean`、`analyze`、`verify`、`report`，依次执行即可从本地会话数据得到诊断报告；`run` 可一次串起全部步骤。
